# KendoOS — Verification & Loop Harness Rules

## 8. 検証・自律修復ループ

### 8.1 検証コマンドとサンドボックス制御

#### A. 基本方針

- 検証は、対象コード、テスト、ガバナンスの実際の状態を確認するために実行すること。
- コマンドの終了コードだけでなく、標準出力（stdout）と標準エラー出力（stderr）の実際の内容を確認すること。
- コマンドの実行結果を確認せずに、検証済みと報告してはならない。
- 環境要因による実行失敗と、コードに起因する検証失敗を区別すること。
- 実行ログを確認できない場合は、検証済みとして扱わないこと。

#### B. Flutter / Dart 公式ツールチェーンの限定例外

以下の公式ツールチェーンコマンドに限り、環境由来の `operation not permitted` が発生した場合は、ユーザーの追加承認を待たずにサンドボックス回避を用いて再試行してよい。

- `flutter analyze`
- `dart format`
- `flutter test`

実行時は以下を守ること。

1. `command -v flutter`、`command -v dart` などで実際の実行ファイルの場所を確認すること。
2. 必要な場合は、確認できた Flutter / Dart SDK の PATH を設定すること。
3. Antigravity が対応している場合に限り、`BypassSandbox: true` を指定して再試行すること。
4. 実際の SDK パスを確認せず、推測で PATH を設定しないこと。
5. サンドボックス回避は、上記の公式 Flutter / Dart 検証コマンドに限定すること。

#### C. 例外の適用範囲外

- ネットワークコマンド、一般的なシステムコマンド、ファイル削除、権限変更、依存関係変更などに、この例外を拡張してはならない。
- 公式ツールチェーン以外のコマンドで権限エラーが発生した場合は、独断でサンドボックスを回避せず、原因と必要な対応をユーザーへ報告すること。
- サンドボックス回避後も公式ツールチェーンが実行できない場合は、8.5 の停止条件に従うこと。

### 8.2 二重ループ制御（Inner Loop / Outer Loop）

検証は、反復修正を効率化する Inner Loop と、最終的な全体整合性を確認する Outer Loop の二段階で管理すること。

#### A. Inner Loop（局所検証）

修正作業中は、変更箇所に絞った局所検証を行うこと。

使用例：

- `flutter analyze <対象ファイル>`
- `dart format <対象ファイル>`
- `flutter test <関連テストファイル>`
- 個別のガバナンス検証スクリプト

目的：

- 修正対象ファイルの静的解析
- 関連テストの実行
- 変更箇所に直接関係するガバナンス検証
- 修正による局所的な回帰の早期発見

- 修正のたびに、プロジェクト全体の静的解析や全ガバナンス検証を繰り返す必要はない。
- 局所検証の対象は、実際の変更範囲と依存関係に基づいて選定すること。
- 関連する局所テストが存在しない場合は、その事実を明示し、代替検証の必要性を判断すること。

#### B. Outer Loop（全体検証）

最終報告前には、変更内容に適用される全体検証を実行すること。

- 検証項目は変更内容、依存関係、回帰リスクに応じて選定すること。
- コード変更を伴わないドキュメントのみの変更などに対して、Flutter の静的解析やテストを機械的に要求しないこと。
- ただし、変更内容に適用されるガバナンス検証やドキュメント検証は省略しないこと。
- 調査・レビューのみの依頼では、コード変更を伴う実装時の検証手順を機械的に適用しないこと。

**B-1. プロジェクト全体の静的解析（ベースライン差分比較）**

```bash
flutter analyze
```

- コード変更を伴う場合は、引数なしで実行し、プロジェクト全体を対象とすること。
- 目標は、今回の変更に起因するエラー・警告が新規 0 件であること。
- コード編集前に既存の `flutter analyze` 結果（ベースライン）を把握できる場合は、編集後の実行結果と比較し、「変更前から存在する既知の警告」と「今回の変更で新たに発生したエラー・警告」を峻別すること。
- 既存の警告を今回の変更によるものと誤認して、無関係なファイルを修正しないこと。
- 逆に、今回の変更によって増えたエラー・警告を「既存問題」と偽って放置してはならない。
- 編集前のベースラインを取得できなかった場合は、その事実を明示し、編集後の結果だけで既存問題か新規問題かを断定しないこと。
- ベースラインとの比較ができない場合は、差分、変更ファイル、関連する解析結果など、確認できる根拠に基づいて判断すること。

**静的解析の判定**

- 新規エラーは 0 件必須とする。
- 新規警告は 0 件を原則必須とする。
- 編集前のベースラインと比較し、既存の警告と今回新たに発生した警告を区別すること。
- 未解決の新規警告がある場合は、理由、影響、対応できない根拠を報告すること。
- 未解決の新規警告を残したまま検証完了として扱ってはならない。
- 未解決の新規警告を残して作業を進める必要がある場合は、ユーザーの判断を得ること。

**B-2. Dart フォーマット検証**

```bash
dart format --output=none --set-exit-if-changed <変更したDartファイル>
```

- 変更した Dart ファイルを対象に、フォーマットが整っていることを確認すること。
- 意図しないフォーマット変更を避けること。

**B-3. 全体ガバナンス検証**

```bash
python3 scripts/run_all_governance.py
```

- 登録されている全ガバナンス検証を実行すること。
- 未実行の検証を PASS と扱ってはならない。
- 失敗した検証について、対象スクリプトと実際のエラー内容を確認すること。

**B-4. 関連テスト**

```bash
flutter test <関連テストファイル>
```

- 変更内容に関係するテストを実行すること。
- テスト対象は、変更範囲、依存関係、回帰リスクに基づいて選定すること。
- 全テストスイートの実行は原則として必須としない。ただし、変更の影響範囲やリスク、ユーザーの指示に応じて実行すること。

#### C. Inner Loop から Outer Loop への移行ルール（状態遷移ガード）

**昇格条件（Promotion Guard）**

- 変更内容に適用される Inner Loop の静的解析、関連する局所テスト、必要な個別ガバナンス検査が合格した場合に限り、Outer Loop（全体検証ゲート）へ移行すること。
- 局所検証でエラーが残っている段階で Outer Loop を実行してはならない。
- 関連する局所テストが存在しない場合は、その事実と代替検証を明示したうえで、局所検証の合格条件を満たしたか判断すること。
- 局所検証が合格した後、追加の無関係な修正を挟まずに Outer Loop へ移行すること。

**降格条件（Demotion Guard）**

- Outer Loop で波及エラーまたはガバナンス違反を検知した場合は、直ちに Inner Loop へ降格すること。
- 原因となった箇所と影響範囲を特定し、局所検証を用いて修復すること。
- 修復後は、昇格条件を再度満たしてから Outer Loop を再実行すること。
- Outer Loop の失敗を無視したまま、完了扱いにしてはならない。

**完了必須条件**

- 最終的なタスク完了報告では、変更内容に適用される Outer Loop の検証結果を明示すること。
- 適用対象の検証が未実行、実行不能、失敗、または結果未取得の場合は、検証完了として報告してはならない。
- ユーザーの指示によって一部検証を実行できない場合は、未実行項目と理由を明記し、未完了として報告すること。
- 条件付き完了とする場合は、未解決事項、影響、残存リスクを明示し、ユーザーの判断を得ること。

### 8.3 テストの選定と実行

- テストは変更内容とリスクに応じて選定すること。
- 既存テストを優先的に再利用し、必要な場合に限って新しいテストを追加すること。
- Unit Test、Widget Test、Integration Test、Replay Test、Governance Test などから、変更に適した検証を選ぶこと。
- 不必要に大量の E2E、Chaos、Golden Test を追加しないこと。
- 既存のテスト範囲、テストの意図、仕様上の保証を理解してから変更すること。
- テストの実行範囲を縮小する場合は、縮小理由と残るリスクを明示すること。

### 8.4 検証結果の厳格な扱い（報酬ハッキング抑止）

- 各コマンドの終了コードと実際の結果を確認すること。
- 標準出力（stdout）と標準エラー出力（stderr）の内容を確認すること。
- 未実行、実行不能、タイムアウト、結果未取得を PASS と扱わないこと。

**コマンド実行ログの確認**

- コマンド実行後は、終了コードだけでなく、標準出力（stdout）と標準エラー出力（stderr）の全ログを確認すること。
- ログが長い場合も、末尾だけで判断せず、全体を確認すること。
- `2>/dev/null` などによるエラー出力の隠蔽や、`| tail` などによる結果の一部だけを確認する方法を、検証結果の判定に使用してはならない。
- `grep`、`sed`、`awk` などでログを抽出する場合も、元のログ全体を確認できる状態を維持すること。
- パイプを使用する場合は、元コマンドの終了コードと出力を確実に確認できる方法を使用すること。
- `set -o pipefail` などを適切に使用し、パイプ内の失敗が隠蔽されないようにすること。
- 実際の出力や終了コードを確認できない場合は、検証済みとして扱わないこと。

**報酬ハッキング（チート行為）の絶対禁止**

以下の行為を、検証を通す目的で独断で実行してはならない。

- 静的解析エラーを回避する目的で、`// ignore:` や `// ignore_for_file:` をコードやテストに追記・挿入すること。
- テストを通す目的で、テストコード内のアサーション（`expect`）を削除・緩和すること。
- 意味のあるアサーションを、`expect(true, isTrue)` などの無意味なアサーションに差し替えること。
- テストの失敗を隠すために、テストを削除、スキップ（`skip: true`）、コメントアウトすること。
- ガバナンス規約の検出対象から対象ファイルを勝手に除外すること。
- 検証条件、閾値、期待値を、実装を通すためだけに変更すること。
- エラーや警告を隠蔽するために、検証スクリプトの判定を弱めること。

**テスト・規約そのものの変更**

- テストやガバナンス規約そのものの変更が必要な場合は、仕様上の根拠と変更の必要性を説明すること。
- ユーザーの承認を得てから変更すること。
- 変更後は、関連するテストとガバナンス検証を再実行すること。

**検証後の変更管理**

- 検証完了後にコード、テスト、設定を変更した場合は、影響する検証を再実行すること。
- 最終検証後にコードを変更していないことを確認してから完了を報告すること。
- 検証結果と最終的な作業ツリーの状態が一致していることを確認すること。

### 8.5 自己修復ループの停止条件とハンドオフプロトコル

- エラーの原因仮説、実施した修正、検証結果を対応づけて管理すること。
- 同じ修正を根拠なく繰り返さず、各試行で仮説と結果を比較すること。

**サーキットブレーカー（即時停止条件）**

以下のいずれかに該当した場合は、自律的な修復作業を停止すること。

1. 同一エラーに対する修正試行が3回失敗した場合。
2. 3回に達していなくても、同一根本原因に対して同じ修正方針を繰り返し、改善が確認できない場合。
3. 修正対象がユーザーの承認範囲を超える場合。
4. テストやガバナンスの合格条件を変更しなければ解決できない場合。
5. 仕様やデータモデルに重大な不確実性がある場合。
6. データ破損、セキュリティ問題、後方互換性の重大な破壊が予想される場合。
7. 依存関係の追加・更新や破壊的操作について承認が必要となる場合。
8. サンドボックス回避後も公式ツールチェーンの実行に失敗する場合。

**停止時のハンドオフ報告フォーマット（Trip Report）**

サーキットブレーカーが作動して作業を停止した場合は、作業ツリーを巻き戻さず、直ちに以下の形式でユーザーへ報告すること。

```markdown
### ⚠️ サーキットブレーカー作動（作業一時停止）

1. **直面している障害（Blocker）**
   - 失敗した検証コマンド：
   - 実際のエラー内容：
   - 発生した条件・タイミング：

2. **試行した仮説と結果（Failed Attempts）**
   - 試行1：[仮説] -> [実施内容・結果]
   - 試行2：[仮説] -> [実施内容・結果]
   - 試行3：[仮説] -> [実施内容・結果]

   ※ 同一エラーの修正試行が3回失敗した場合は「Failed Attempts: 3/3」と明記する。
   ※ 3回未満、または別の停止条件の場合は、実際の試行回数を記載する。

3. **変更済みファイル**
   - [ファイルパス]
   - [変更内容の概要]
   - 現在の作業ツリーの状態：

4. **ユーザーへ求める判断（Decision Needed）**
   - 方針A：[選択肢とその影響]
   - 方針B：[選択肢とその影響]
   - 推奨：[推奨案と理由]
```

**停止時の保全ルール**

- 勝手に作業ツリーを破棄・巻き戻さず、人間の診断用に現状を保全すること。
- ユーザーの既存変更とエージェントの変更を区別して報告すること。
- 自己修復のために無関係なファイルへ変更を拡大しないこと。
- 停止後は、ユーザーの判断・承認があるまで修復作業を再開しないこと。
- 作業停止を理由に、既に行った変更を隠したり、失敗した検証を PASS と報告したりしてはならない。

### 8.6 完了条件

タスクの完了状態は、以下の3区分で管理すること。

**1. 検証完了**

以下をすべて満たす場合に限る。

- 依頼された変更が実装されていること。
- 変更範囲が承認された範囲内に収まっていること。
- 編集後の差分を確認し、意図しない変更がないこと。
- 変更内容に適用される Inner Loop の局所検証が合格していること。
- 変更内容に適用される Outer Loop の全体検証が合格していること。
- 既存の問題と今回の変更による問題を、確認可能な根拠に基づいて区別していること。
- テストやガバナンスの条件を弱めていないこと。
- 検証後に追加変更を行っていないこと。
- 未解決の新規エラー・警告がないこと。

**2. 条件付き完了**

- 実装自体は完了しているが、未解決の新規警告、実行できなかった検証、その他の残存リスクがある状態。
- 未解決事項、発生理由、影響、残存リスクを明示すること。
- ユーザーに判断を求め、判断結果を報告に残すこと。
- 条件付き完了を検証完了として扱ってはならない。
- 未解決の新規エラーや重大な安全性・データ整合性の問題を、条件付き完了として安易に許容してはならない。

**3. 未完了**

以下のいずれかに該当する場合。

- 依頼された変更が完了していない。
- 必要な検証が未実行、実行不能、失敗、または結果未取得である。
- 必要な承認やユーザー判断が得られていない。
- 重大な問題やリスクが解決していない。
- 作業を停止してユーザーの判断を待っている。

- 実行していない検証を、実行済み・合格として報告してはならない。
- 3区分のいずれに該当するかを、最終報告で明確に示すこと。

## 9. テスト失敗・コミット拒否への対応

### 9.1 テスト失敗時

- テストが失敗した場合は、まず失敗箇所、エラー内容、再現条件を確認すること。
- 既存のテストログがあり、今回の失敗との関連性がある場合は、`test_last_run.log` などの記録を確認すること。
- 古いログを、今回の実行結果であるかのように扱わないこと。
- テストの失敗を隠す目的で、テストやガバナンスを変更してはならない。

### 9.2 コミットフック拒否時

- コミットフックが拒否した場合は、拒否理由を確認すること。
- フックを無効化したり、スキップしたりしてはならない。
- ユーザーの承認なしに、コミットを強行してはならない。
- 原因を解決できない場合は、拒否内容と対応案を報告すること。

## 10. ガバナンス規約の追加・変更

### 10.1 変更前の確認

ガバナンス規約を追加・変更する場合は、以下を確認すること。

- 既存のガバナンススクリプト
- 番号体系と登録ルール
- `run_all_governance.py` の実行対象
- 関連する仕様書・テスト
- 既存規約との重複・矛盾

### 10.2 追加・変更方針

- 既存規約の強化で対応できる場合は、新規スクリプトを安易に追加しないこと。
- 新規スクリプトが必要な場合は、追加理由と既存規約では不足する理由を説明すること。
- 新規検証を追加した場合は、`run_all_governance.py` に適切に登録すること。
- 検証対象、判定条件、エラー時の挙動を明確にすること。

### 10.3 検証

- 個別スクリプトの実行結果を確認すること。
- 全体ガバナンス検証への登録を確認すること。
- 最終的に全体ガバナンスを実行し、結果を報告すること。
- 既存のガバナンスを弱めて新規規約を通してはならない。

## 11. ドキュメント・仕様書との整合性

実装・変更時には、対象機能に関連する既存ドキュメントを確認すること。

確認候補：

- `docs/governance/architecture_invariants.md`
- `docs/governance/governance_constitution.md`
- `docs/governance/core_philosophy.md`
- `docs/governance/replay_truth.md`
- `docs/governance/replay_compatibility_policy.md`
- `docs/governance/operational_validation_protocol.md`
- `docs/governance/sync_scope_definition.md`
- `docs/governance/sync_conflict_policy.md`
- `docs/governance/rule_testing_standard.md`
- `docs/governance/rule_package_spec.md`
- `docs/domain/match_lifecycle_fsm.md`
- `docs/domain/firestore_public_schema.md`
- `docs/domain/glossary.md`

- 上記は確認候補であり、実際のファイルの存在とパスを確認すること。
- 存在しないファイルを存在するものとして扱わないこと。
- 仕様書と実装が矛盾している場合は、独断でどちらかを正として変更せず、矛盾箇所と影響を報告すること。
- 仕様変更が必要な場合は、コード変更より先に仕様の確定を求めること。
